# Owner guard and merge helper

These files protect every commit, push and merge in this repository. They were moved here from the
shared governance skill (`~/.codex/skills/tear-program-governance`), which still serves the music
and wiki repositories unchanged.

| File | What it does |
| --- | --- |
| `hooks/` | Five `sh` wrappers (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `pre-merge-commit`, `pre-push`) that run `tear-git-guard.mjs` with Node. LF endings are pinned in `.gitattributes`. |
| `tear-git-guard.mjs` | The rules below. |
| `owner-safe-pr-merge.mjs` | Squash-merges a pull request as the owner, only with `--authorize-owner-merge`, the exact reviewed head, a green `check` and a clean subject and body, then verifies the merge commit. |
| `setup-hooks.mjs` | `pnpm setup:hooks` points this repository at `hooks/` and pins the owner identity; `pnpm check:hooks` reports which hooks a clone or worktree uses. |

## Rules the guard enforces

Every hook first checks the installed policy:

- the origin is the exact canonical URL;
- `core.hooksPath` is this folder;
- `user.useConfigOnly=true`;
- user, author and committer are the owner;
- the Git common directory matches the one recorded at install.

Then, for each hook:

- **pre-commit, pre-merge-commit:** the effective author and committer are the owner, including `GIT_AUTHOR_*` and `GIT_COMMITTER_*` overrides and `--author`. The branch is a `codex/<scope>` branch, not `main`, `master`, a legacy or oracle branch, or a detached HEAD.
- **prepare-commit-msg, commit-msg:** the same checks, plus the message carries no attribution. Forbidden:
  - trailers such as `Co-authored-by:`, `Signed-off-by:`, `Generated-by:`, `Reviewed-by:`, `Created by:`, `Built by:` and `Tested by:`;
  - phrases such as "generated by Claude" or "written by an AI".

  The message is normalised for Unicode hyphens, CRLF and invisible characters first. `prepare-commit-msg` runs even when a commit asks Git to skip hooks.
- **pre-push:** the remote is `origin` at the exact URL. Every pushed ref must:
  - be the current `codex/<scope>` branch, pushed to the same name;
  - be a fast-forward (no force pushes, no deletions);
  - share history with `origin/main`. It need not contain main's newest commit: a branch may be behind main, and may take main in with `git merge origin/main`.

  One deletion is allowed (owner decision, 2026-11-16): a remote branch whose name is exactly a batch branch, `codex/batch-YYYYMMDDtHHMMSSz` (`pnpm merge:batch --prune`). Every other deletion is refused. The shared skill copy of the guard still refuses all deletions; the music and wiki repositories have no batch branches.

  Every commit the push publishes (not on the remote branch and not on `origin/main`) must be owner-authored, owner-committed and free of attribution. Commits already on `origin/main`, including GitHub's squash merges brought in by `git merge origin/main`, are not re-scanned.

The merge helper additionally refuses:

- a repository path that is not one of the three canonical checkouts;
- a checkout not on `main`;
- a GitHub login other than the owner;
- a pull request that is not open, not into `main`, from a fork, or with a moved head;
- a pull request without a green `check`;
- a pull request with any non-owner commit, unless it is the exact wiki synchronization bot pull request (tear-wiki only; its file set is `WIKI_SYNC_FILES`, in one place at the top of the helper).

New refusals go in `MERGE_PRECONDITIONS`. It is an ordered list of `{ id, check }`, each with its own test, and it runs after the checks above and before anything is merged. It holds one rule today, for the game repository only: `merge-ready`. It refuses unless `scripts/merge-ready.mjs` says READY. That means main's newest commit is checked and green, and the pull request's pass is not older than a main change to its files or to shared files. A pull request is also READY when a passed batch run (`pnpm merge:batch`) covers it. This is the one place freshness is enforced, now that pre-push accepts branches behind main.

## Setup

Run once in the canonical checkout, on `main`, after this folder is on `main`:

```
pnpm setup:hooks
```

It is idempotent. It replaces only the shared skill hooks or no hooks, and refuses any other hooks path. Linked worktrees share the repository config, so they use the same hooks. The hooks path is absolute and points into the canonical checkout, so a feature branch cannot weaken the guard that checks it.

**Per-worktree overrides.** With `extensions.worktreeConfig` on, a worktree's own `config.worktree` can set `core.hooksPath`, and that wins over the repository setting. Every linked worktree here once carried one pointing at the shared skill hooks, next to `core.longpaths = true`. After the switch, Git ran the shared hooks, and those refused because the repository setting named the in-repo hooks.
- `pnpm setup:hooks` removes such overrides when they point at the in-repo hooks or at the shared skill hooks, in every worktree. It refuses any other override, before changing anything.
- `pnpm check:hooks` reads the hooks path Git actually uses in this worktree, and names every worktree whose override points elsewhere.

What writes these overrides is not established. They appeared only in worktrees created by tooling, never by the setup script. Run `pnpm check:hooks` after creating worktrees, and `pnpm setup:hooks` from the canonical checkout if it reports one.

## Keeping the two copies in step

The copy here is the authority for this repository; the shared skill copy remains the authority for the music and wiki repositories. `tests/unit/governance-guard.test.mjs` runs every rule case against both copies when the shared copy exists on the machine, so a difference in behaviour fails locally. CI has only this copy.
