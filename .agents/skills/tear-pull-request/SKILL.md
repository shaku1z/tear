# Tear pull request

The rules live in `AGENTS.md` ("Hard rules", "Finishing"),
[docs/RELEASE_AUTHORITY.md](../../../docs/RELEASE_AUTHORITY.md) ("Merging") and
[scripts/governance/README.md](../../../scripts/governance/README.md). This is the order to apply them in.
Where this skill and those disagree, they win.

## 1. Start

- One task, one worktree, one branch named `codex/<scope>`, cut from `origin/main`. `pnpm who` lists every
  worktree with its branch and state. Never edit the canonical checkout or share a worktree.
- `pnpm check:hooks` says whether the commit and push guards are active.
- A task that spans pull requests or sessions gets a card from `plans/TASK_CARD_TEMPLATE.md`.

## 2. Commit and push

- Commit as the configured owner identity. No co-author, sign-off or "generated by" line anywhere: the
  hooks reject them. Never use `--no-verify`, never force push, never rewrite pushed history.
- `pnpm format`, then `pnpm check:quick`, then push. Push early so the work does not exist only locally.
- The repository is public. Nothing private goes in a commit, a description or a comment.

## 3. Open the pull request

- Fill every section of `.github/pull_request_template.md`. The description becomes the squash commit
  body, so it carries no attribution either.
- Answer all six design-check labels of
  [docs/ENGINEERING_STANDARD.md](../../../docs/ENGINEERING_STANDARD.md) in the template's form
  (`- **Cause:** …`). "n/a" needs a reason after it. `pnpm merge:ready` refuses a missing or empty answer.
- A draft does not run the required check. Open as a draft to publish work in progress, and mark it ready
  when it should be checked.
- If the change moves a workstream's state, edit that area's file under `config/position/` and run
  `pnpm position:render` in the same pull request.

## 4. Keep it current

- When `main` moves or the pull request conflicts: `git merge origin/main` on the branch, then push. Never
  rebase (the commit guard refuses a detached HEAD, and a pushed branch cannot be force pushed), and never
  cut a second branch or a replacement pull request.
- The required check always judges the change merged with `main` as it is when the check starts. A branch
  may be behind `main`; freshness is decided at merge.
- A failed check is fixed at its cause and pushed. Do not re-run an unchanged run hoping it passes.

## 5. May it merge?

`pnpm merge:ready <pr>` answers yes or no with the reason. It needs all of:

- the latest finished Validate run on `main` passed (unless the pull request is labelled `fixes-main`);
- the pull request's own run passed for its current head, and `main` has not since changed a file it
  touches or a shared file. `pnpm merge:ready <pr> --refresh` starts a fresh run when the pass is stale;
- the design check is answered;
- a change to a gate file (`config/gate-files.json`) has been cleared by the lead.

## 6. Merge

- One pull request: `node scripts/governance/owner-safe-pr-merge.mjs` with `--authorize-owner-merge`, the
  pull request number and its exact head commit. Run it without arguments to read its usage. It squashes as
  the owner, refuses unless `merge:ready` says READY, and verifies the merge commit.
- Several: `pnpm merge:batch [<pr> ...]` builds a `codex/batch-<time>` branch and checks the combination
  once; `--status`, `--merge <branch> --authorize-owner-merge`, `--verify` and `--prune` follow it up.
- Two stacked pull requests that must land together are not two batch members: a squash of the first can break
  the second. Merge the first, take `main` into the second, then merge it.
- A pull request that changes `src/gameplay/run/ruleset-version.ts` merges alone, never in a batch, and in
  the order the lead fixes: two of them each bump from the same number, and the second must take `main` and
  bump again.
- Never `gh pr merge` directly, and never `--admin` or `--auto`.
- Who merges is a working arrangement, not a rule of this skill: when a lead reviews and a merge desk
  merges, hand over the pull request link and head instead of merging your own.

## 7. Afterwards

- Tell the owner what merged. Deploying is separate: the deploy workflows start from a green Validate run
  on `main` ([docs/RELEASE_AUTHORITY.md](../../../docs/RELEASE_AUTHORITY.md)); nothing local can publish.
- Remove the worktree and branch only after the work is on `main`, after checking for uncommitted work.
  If `node_modules` is a junction, remove the link alone first (`AGENTS.md`, "Known traps").
- `pnpm leftovers` lists merged local branches and stray files. It deletes nothing.

## Limits

Credentials, rulesets and branch protection, force pushes, history rewriting, bypassing a failing check,
and the music and wiki repositories need the owner. Stop and ask.
